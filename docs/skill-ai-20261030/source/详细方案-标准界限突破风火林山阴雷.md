## 二 处理原则

### 分四档审查而不是统一重写

| 档位 | 处理 | 证据要求 |
|---|---|---|
| P0 正确性 | 规则/合法性/触发入口/错误状态/崩溃优先修复 | 源码和最小复现场景；明确原行为与正确行为 |
| P1 策略结构 | 联合目标、数量、分支或短序列，单项评分难以表达 | 至少一个有意义的候选策略与反例；序列验证 |
| P2 局面估值 | 支付成本、目标收益、阶段/血量阈值和能力标签 | 固定局面和对照数据 |
| P3 保留优先 | 没有自主选择或已主要复用通用牌效的技能，先做兼容回归 | 无缺陷/退化证据时保留；不以AI字段多少判好坏 |

逐将表的初始排期为P1 56个版本、P2 75个、P3 11个。这是按机制分配工作量的候选清单；P3也需回归被其他角色攻击时的效果估值，P1也可能最终无需修改。

### 保留现有有效逻辑

原代码已有的花色规划、判定分析、响应能力声明、阶段限制不能被更粗的通用函数替换。许攸成略已分析伤害牌花色和距离/次数用途，应保留为对照，而不是退回「低价值牌先弃」。

## 三 先形成共同评估能力

这些是拟议的评估职责，不是声称本体已有同名API。先盘点get.effect/get.value/getUseValue、技能标签和事件接口能覆盖什么，仅补缺失部分。

| 评估职责 | 输入 | 输出 | 适用例子 |
|---|---|---|---|
| 行动合法性 | 当前事件、h/e/s区域、目标、次数、技能状态 | 合法候选及不合法原因 | 转化、改判、移牌、重铸 |
| 资源机会成本 | 自己已知牌、血量/上限、阶段、后续用途 | 消耗一张牌/一点体力/装备栏的代价 | 苦肉、奇谋、强袭、决堰 |
| 目标净收益 | 获牌/失牌/受伤/失血/回复等变化 | 在指定观察视角下的效用 | 突袭、仁德、节命、天香 |
| 技能反应修正 | 受影响角色的相关机制及当前触发条件 | 有限的边际收益修正 | 失牌收益、卖血、空手、觉醒门槛 |
| 联合选择 | 支付牌、目标组合、数量、分支 | 可比较的完整候选 | 缔盟、离间、结姻、溃诛 |
| 近期兑现 | 当前已知手牌、剩余阶段/次数 | 有限后续行动收益 | 裸衣、天义、神速、雄乱 |
| 风险和停止 | 不确定响应、当前生存资源、搜索预算 | 风险折扣、停止或回退 | 苦肉循环、乱武、化身 |

必须分清效用视角：`get.effect(..., viewer)`通常已经含态度权重；`ai.result.target`描述对目标的作用，不能再机械乘一遍敌友关系。每个共享评估接口需要声明视角与单位，避免损益重复计算。

技能决策不以武将姓名为条件；角色版本ID可用于补丁启用范围、兼容性及日志登记。这两种用途要分开。

## 四 从乐曹植反馈提炼出的实施规则

1. 不在计算组合收益前就以单张牌的保留成本淘汰组件。闪在回合内的边际价值，与可继续过牌和回合外风险一起计算。
2. 不让「知道配对有收益」只停留在辅助函数，必须接入实际使用顺序、支付牌和选目标入口。
3. 把使用、打出、重铸、弃置、失去体力、受到伤害分开，不能因为都减少资源就共用错误触发语义。
4. 多步技能比较整条路线；阶段替代技能比较替代前后收益。不能每个局部选择独立贪心。
5. 不把未知摸牌、随机牌名或对手响应当成已知组件；公开信息和技能实际揭示的信息才可作为输入。
6. 每次真实结算后重算，不机械执行过期计划。缓存只可复用引擎承诺稳定的同一次比较上下文。
7. 规则检查先行；合法但单独收益较低的准备动作可参与组合比较，不为补牌奖励抬高明显伤害队友的动作。
8. 搜索只给确实需要的复杂技能；无选择的被动技能不应套四步搜索。

## 七 外部测试人员的工作协议

### 第一步 固定环境

每名测试者登记：客户端和引擎版本、实际加载源码哈希、补丁哈希、已启用扩展及顺序、模式、人数、身份规则、禁将/牌堆设置、设备和浏览器内核。确认补丁实际应用，跳过或不匹配必须单独记录。

不得把「上游main」当版本标识；使用本方案固定SHA或明确列出的本地执行基线。每批冻结对手策略版本；强将环境和经典环境分开统计。

### 第二步 固定场景

由开发者/测试者共同建立初态：武将ID、技能ID、身份/座位、血量/上限、h/e/s区域、装备/判定、标记、翻面/连环、历史计数、阶段和合法目标。

每个场景先明确规则上允许哪些动作，再定义「不能犯的错误」与可接受行动集合，不把唯一手工指定动作当作全局最优。对新策略的优势例和反例都要测试。

测试必须覆盖真实引擎调用和结算，不能只调用评分函数。对关键组合记录2—4步序列，确认每一步的技能触发和资源变化。未知摸牌不通过人为指定理想结果来证明策略强。

### 第三步 原AI与候选AI对照

- A：固定基线原AI；B：只启用这一项候选改动。先单变量，不一次开整个包。
- 使用配对初态/初始牌堆，轮换身份和座位。正常对局允许行为导致后续轨迹不同。
- 同一个随机种子不保证两种策略抽到同样的牌：动作可能消耗不同随机次数。能分离牌堆随机与策略随机时分别固定，否则记录限制。
- 重点人物的队友和对手策略保持一致。多人局按对局/配对初态作为统计聚类单位，不能把同局所有决策当独立样本。
- 不使用人工看得到全部手牌的信息喂给受测AI。裁判可另存全状态用于离线诊断，但与决策输入分离。

### 第四步 跑局与报告

先跑少量固定场景和预算明确的试跑，发现崩溃/非法/漏触发立即回到复现，不用大量随机局掩盖错误。扩大局数前先看身份/座位覆盖和误差区间。样本量由观察到的不确定性、目标精度和算力决定，不给所有技能统一指定「跑多少局必然够」。

至少报告：有效场景数/局数、未应用比例、可避免错误率、技能实际兑现收益、关键资源无效消耗、停止/回退次数、决策耗时分位数、胜率及差值的区间。记录崩溃和超时的分母，不能删除失败局后只汇报成功局。

短期触发次数和摸牌量只是诊断指标，不是单独优化目标；过度触发、伤害队友、为了觉醒送命均可能提高局部数值却降低整体表现。

## 八 日志字段

`决策日志模板.json` 是空模板，不含任何实测数据。

| 字段组 | 必填内容 |
|---|---|
| 版本 | 上游SHA、实际引擎文件哈希、补丁版本/哈希、应用状态 |
| 实验 | run/match/pair/decision ID、场景ID、测试者、随机源标识 |
| 对局 | 武将ID、技能ID、模式、身份、座位、对手策略、其他扩展 |
| 观测 | 允许信息范围、初态/观测哈希、阶段、合法动作 |
| 决策 | 候选动作及分解收益、所选动作、引擎实际执行动作、耗时、搜索节点和回退 |
| 结算 | 实际事件、触发是否成立、资源变化、错误标签、最终结果、录像路径 |

角色/牌用稳定ID序列化，避免直接JSON.stringify完整player/card对象造成循环引用。错误标签建议区分：未应用、非法候选、漏触发、目标判断、支付牌、数量/阈值、顺序、过度保牌、过度发动、信息范围、性能、未分类。

每条异常至少给一个可复现初态或录像，附具体版本和决策ID。「不聪明」「没摸牌」可作为线索，不能独立作为修改验收标准。

## 九 交付和验收

### 每项候选的状态流转

`待审查 → 源码证据 → 可复现问题 → 候选方案 → 固定场景通过 → 小规模对照 → 扩大验证 → 保留/调整/放弃`

任何环节都可以判定保留原AI。未复现、数据不足或版本不匹配不计作优化成功。

### 可实现时的验收门槛

1. 规则、区域、次数、响应和濒死行为不退化；没有额外全信息输入。
2. 已确认反例通过真实入口与结算验证，且反向场景不产生明显新误操作。
3. 标准/界版本、共享/借用技能影响有明确记录；自动回退有效。
4. 在目标设备上的计算预算可接受，超出预算有安全回退；不能只报平均耗时。
5. 对照报告包含失败、区间和分层结果；没有可靠收益就保留原AI。
6. 人工复盘关键录像，检查胜率变化是否来自越权信息、规则变化、对手版本或场景偏差。

不在当前阶段设置「所有武将胜率必须提高多少」之类没有数据支持的承诺。

## 十 工作组织与本次交接物

推荐采用「共同评估职责＋逐技能薄适配＋有限专项规划」，优先做A1—A6的少量代表技能。逐将全部重写维护成本高；只调常数不能解决结构性顺序问题；给所有技能套搜索会增加复杂度和耗时。

分工：
- 代码审查者：展开真实技能依赖，定位全部决策入口，写反例与候选策略。
- 实现者（后续另行安排）：只实现已确认的一项候选，不随意扩大范围。
- 测试人员：依协议跑固定场景和对照，提交原始日志、录像、环境信息及摘要。
- 复核者：检查规则、信息范围、统计口径及是否保留原策略。

本目录交接：
- `逐将审查与测试任务.md`：142个版本的技能、优先级、候选方向和机制场景。
- `武将技能清单.json`：范围、源码定位、登记技能、AI入口信号和文件清单。
- `测试任务清单.json`：142项机器可读候选任务，全部标记未实现/未测试。
- `决策日志模板.json`：待填写空模板。
- `本地与上游版本对照.json`：执行基线与参考基线对照。
- `GitHub源码清单.json`：提交、Git blob SHA和来源URL。

任务JSON标记 `execution_ready:false`：它是任务协议，不是能直接启动游戏的自动跑局脚本。测试者需按约定补全场景初态和运行器。当前未编写/部署跑局器，没有向任何人发送消息，也没有改动已有扩展。
