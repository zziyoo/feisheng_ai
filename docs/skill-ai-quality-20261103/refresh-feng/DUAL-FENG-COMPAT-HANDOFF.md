# 双风兼容：冲突分析与独立验收交接

基线 `3fefae2581c168dc753ebabe003c1658911b7b7c`；开发分支 `codex/dual-feng-compat`。新版共享入口、租约及安装器准入已作为源码候选实现，**整体共存仍未完成：原生组合补丁尚缺，运行时与安装候选未验证**。旧包仍互斥。神话风烈弓单包修复有独立专项验收；本次继续开发未运行任何执行式验证。

## 2026-11-09 收尾改动及未完成项

- Windows 行尾：安装器对共享 JS 的完整 CRLF 检出与 LF 包进行严格字节往返识别，仅给出迁移诊断，依然拒绝写入；BOM、混合行尾、内容差异不视为兼容。由于模板字符串等可能对行尾敏感，未将归一化视作语义等价。退出宿主后备份原始字节和全部安装记录，确认共享核心所有者全部安全回滚并可恢复后，再人工迁移为包内精确 LF 字节；仍有使用者时不得迁移。此为明确拒绝和迁移方案，最终默认发布包在 Windows 的实际安装尚待验证，P1 未关闭。
- 双风 `manifest.package.wind_compatibility` 直接取自 `pack.json` 的协议和对包哈希对象。安装器依旧检查对包真实哈希与共享核心字节，不仅依赖分包名。
- 批量安装仍是全有或全无；失败后通过 `installSkillAIPolicyPack` 可在空宿主单独安装兼容包，或在已安装宿主增量安装；全量重复配置报错指明替代入口。失败状态保留实际宿主是否仍安装及失败原因。`stats()` 先合并各子宿主的 `packs` 再按既有规则填充顶层字段；同名字段取第一个，不能视为累计值，按包统计用于区分所有权。
- **尚未生成双风组合原生补丁**。两个原生补丁不得叠加；组合原生与扩展同时接管同一入口尚无安全证明，也不得声明支持。须从干净基线构造完整组合修改并交给独立 Agent 检查应用、语法与技能结算。
- 独立 Agent 应覆盖 LF、CRLF、混合行尾、BOM、真实改动、标准包持有共享核心、迁移后回滚的原字节、双风及旧版混装；复核 manifest 和 pack 声明、失败后的单包注册、按包卸载重装及扁平与分包统计；另按下文完成组合原生及宿主场景。以上均未在本轮运行。

## 续作状态与实现

* `policyCore.js` 的 `wrapShared` 将宿主 `owner`、回调键与协议契约绑定在共享 WeakMap 中，保留一份原始回调和一层协调包装；参与包各有一个所有权令牌。协调器按分包 ID 的确定顺序调用一份处理函数，不串联、不相加。当前两包声明同一个烈弓契约，其候选的收益分支均在满足相同条件时返回 `num + 7`；神话风统计计数只在其处理函数被选中时增长，不能据此判断另一包未注册。
* `uninstallPack` 按包清理回调和所有权，最后一个共享所有者退出且当前属性仍为协调器时恢复原函数。第三方已改写属性时保留外部代码，失去全部所有者的协调器退化调用原函数；再次注册遇到外部包装时拒绝。其他普通 `host.wrap` 仍采用原有按引用恢复方式，若它们被第三方捕获，不能保证对象引用完全恢复。
* 运行时沿用旧全局风包租约 Symbol；新版租约带 `dual-feng-shared-entry-v1` 协议和分包令牌，旧核心看到非空租约仍拒绝混装。新版拒绝旧租约、无协议的旧风包及同一分包的另一实例；发现已标记的旧版烈弓包装残留也拒绝。新增 `installPack` 用子宿主增量重装分包，失败时保留此前宿主；对应 facade 新增按包安装、卸载方法。主 `install()` 仍不接受直接替换整个配置，热重装和异常隔离均待验证。
* `apply-pack.mjs` 对已有对包导入要求本包声明相同协议、预期对包模块名及精确对包 SHA256；共享核心仍通过原有字节哈希预检。构建配置为新版两包记录对方 Git 源文件哈希。新版/新版仅在源码与共享核心匹配时尝试准入；旧安装器、新旧混装或不一致核心继续拒绝。共享核心已有标准包的旧版本时不能覆盖，需先确认所有现有分包兼容并通过受控迁移。停止宿主后备份、按记录回滚旧风包，核对其他包与共享核心，再迁移新版并重启；不可使用 `--force`。
* 上述仅为源码候选，未证明两种安装顺序、异常回滚、外部修改和运行时生命周期正确。特别要检查外部改写后清理异常、重复卸载和重装，以及共享入口注册失败后是否残留 lease 或包装。

## 原生组合补丁尚未交付

不得直接将两份补丁拼接或依次强制应用。需针对同一份 1.11.7 干净源码独立构造一份组合候选：狂骨在低血优先恢复、可兑现杀和恢复/摸牌收益比较之间确定不重复的统一选择；神速按真实技能和跳过判定条件选择一致的收益门槛；烈弓只保留一次带剩余杀次数检查的加权分支。再保留所有非冲突 hunk，包括界风 `buqu` 与 `piaoling`。这些重叠回调的统一策略仍需明确并复核，现阶段不能声称原生双包兼容或两份候选可以连续应用。单包补丁均保留未覆盖。

## 上一轮代码与限制（历史）

`score/decision/skills/packs/shenhuaFeng.js` 的 `installLiegong` 增加 `player.getCardUsable('sha') > 0`，成功分支仍使用已有 `num + 7`，调用失败回退原函数。此为待验证候选；它不保证原函数自身不会加权，尤其不覆盖已应用旧神话风原生补丁的情况。未删除任何安装互斥、租约或旧包保护。

两个分包各在独立 host 安装时，简单删除租约会重新暴露包装链残留；两个包在同一 host 安装时，现有 `uninstall()` 是整组卸载，并不提供按包卸载 API。旧 ZIP 将旧核心哈希和旧策略一并携带，故需协调双方兼容版及共享核心，不能强制覆盖。现阶段无法在保留上述属性的前提下仅凭此局部改动安全放行。禁止将本提交描述为共存修复完成。

## 上一轮兼容设计记录（历史，状态以顶部续作说明为准）

1. 在共享核心为真实 `owner + key` 建立有所有者的入口租约，以 `skillId + callbackPath + scope` 作声明和诊断；对未知的重叠策略默认安装前拒绝。`xinliegong.mod.aiOrder` 只注册一个协调器，双方显式声明同一兼容规则，避免两次加分；不因为名字相同就吞掉不同语义的策略。
2. 协调器将活动所有者与宿主原函数分开；按包移除时仅撤销该包所有权，最后一个所有者移除时，在对象仍指向协调器的情况下恢复原函数。外部包装或替换时不覆盖外部修改；对于外部闭包仍引用协调器的情况令其退化为调用原函数，并明确对象引用可能无法恢复。安装失败需撤销已取得的各项所有权与其他包装，再恢复注册状态。需考虑异步重入、异常与多模块实例；不得在同一 host 将所有其他分包一起卸载来冒充分包卸载。
3. 为防旧核心绕过新协商，必须同时设计跨 `?v=` 模块实例的共享版本标识和旧 `exclusive-wind-lease` 安全握手；无法确认旧版本时拒绝。两个新版候选需使用字节一致的共享核心、安装器及明确版本；现有 SHA 校验与事务记录继续生效。旧包先备份和回滚，再在隔离目标安装同版本的两个新版候选。不得直接覆盖旧核心或绕过其哈希。
4. 单独制作基于同一宿主基线的组合原生补丁，对狂骨、神速、烈弓逐项确定语义后只保留一个真实回调，保留其他不相交修改；与扩展接管同技能仍应避免重复叠加。两份原生补丁的两个应用顺序和组合补丁都必须由独立 Agent 实际检查，不能由静态观察推断通过。

## 独立 Agent 验收交接

在隔离宿主先验证本轮神话风单包：调用真实 `xinliegong.mod.aiOrder`，杀余量 0 和 1 各检查实体无中、合法目标和回退；记录原函数、扩展包装及最终行动，检查未启用该包的行为。此后仅当协商实现完成，再进行以下双包验收：

- 两种安装顺序、各自重复安装、分别卸载及两种重装顺序；检查注册行、租约、评分调用次数和最终可用函数对象。
- 不同共享核心、重复入口声明、写入中途失败、注册后异常、租约清理失败、旧包混装、CRLF 差异与外部改动；核对所有权、事务记录和零残留。
- 真实宿主分别触发两包独立策略和共享烈弓入口，验证不存在重复加分，单包卸载后另一包仍可运行，其他包与 134 维契约不受影响。
- 分别应用两个原生候选并检查两种叠加顺序；如冲突，用新设计的组合补丁重新应用和检查结算，并复验不屈、飘零和已有历史技能。原生与扩展的共存结论分别记录。
- 最终新包必须重建并检查 Git blob 字节、manifest、哈希、安装、回滚与重装；旧 ZIP 不覆盖。只有所有相关检查有证据后才能声明兼容通过。
